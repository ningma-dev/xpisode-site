# 本仓库是怎么组织的

只想照着操作的话，不用读这篇。

## 只放部署

任何一台电脑坏了，配置能从 GitHub 恢复，已上传的数据能从 OSS 恢复。没上传的数据和本机的钥匙恢复不了。

## 一台机器人一个目录

```text
robots/<站点>/
  station.toml   这台机器人有哪些设备、怎么录
  can.toml       每条手臂用的 CAN 适配器序列号
  tuned/         每条跟随臂的调参结果
  machine.md     装机时的硬件快照，以后拿来对比
  LOG.md         在这台电脑上做过的事
```

- 只有一个 `main` 分支。每台电脑都拉同一份，各自读自己的目录。
- 每台电脑在仓库里有一个不提交的 `.station` 文件，写着自己是哪个站点。脚本只从这里知道站点，没有参数或环境变量能改它。
- `robots/_template/` 是新建站点用的模板。
- 目录名就是站点名，每条录制都会记下它，定下来就不改。

## 三个容易问的为什么

**CAN 适配器为什么按序列号起名？** 这样适配器插在哪个口都不影响名字。四个名字在每台 YAM 上都一样（`can_follower_l` 等），所以各台的站点文件只有序列号不同。

**后台任务为什么要避开某些 CPU 核？** 每个 USB 控制器由一个固定的核处理。上传、生成视频这些后台任务如果跑在相机用的核上，相机会丢帧。脚本每次启动时查一遍相机和 CAN 现在用的是哪几个核，把后台任务放到其他核上，所以换了插口也不用改配置。

**为什么关掉相机的 USB 省电？** 相机闲置两秒就会被系统挂起。下次启动站点时要先把它唤醒，唤醒失败，相机就打不开。

## 脚本

每件事只有一个脚本，在机器人电脑上只用下表里的。不要直接运行 `.venv/bin/xpisode`、`scripts/oss.py` 或底下的 Python 工具：那样不读 `.station`，要手抄站点名、序列号这些站点文件里已有的东西，后台任务也不避开相机用的核。

| 脚本 | 做什么 | 会改系统吗 |
| --- | --- | --- |
| `host/setup.sh` | 系统设置 | 会，要 sudo |
| `host/can_rules.py` | 生成 CAN 命名规则 | 加 `--check` 只预览；不加要 sudo |
| `host/doctor.sh`、`host/snapshot.sh`、`host/devices.sh` | 体检、快照、列出设备 | 不会，也不让相机开始拍摄 |
| `scripts/run.sh` | 启动站点；`--file` 选本站点目录里的另一个站点文件 | 手臂会动，要有人在场 |
| `scripts/serve.sh` | 网页面板 | 不会 |
| `scripts/tune.sh` | 给一条跟随臂调参，结果存到本站点的 `tuned/` | 手臂会动，要有人在场 |
| `scripts/gello.sh` | GELLO 主臂：设舵机编号、标定、检查 | 不会；手臂不动，只用 GELLO |
| `scripts/save_pose.sh` | 把手臂现在的位置存成预设姿态（站点要在运行） | 不会 |
| `scripts/camera_baseline.sh` | 相机丢帧对照组（`tools/camera/`） | 会打开相机，要约好时间 |
| `scripts/oss.sh` | 和 OSS 之间的一切：`push --follow` 是自动上传，`status` 看还有什么没传 | 不会 |

## 在 Mac 上同时改几个仓库

把代码仓库克隆到本仓库旁边，运行 `scripts/dev_link.sh`，本仓库的环境就会用你改过的源码。`uv sync --locked` 恢复到写定的版本。
