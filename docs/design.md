# xpisode 设计

日期：2026-11-10。状态：草稿，待人工检查。

这份文档从头给出 xpisode 的设计，取代 ADR 0001–0023。它不是对旧决定的汇总：保留的部分是因为重新想过之后仍然成立，改掉的部分在正文里标了 **【改】**，表示和今天的实现不同。需要你拿主意的地方标了 **【你定】**，集中在第 12 节。

字段、消息、路径的精确定义在 `repos/xpisode/docs/reference/` 的规范里，这里只讲结构和理由。

## 0. 锚定的思路：一张只追加的读写图

后面各节的提议，一条条看都有道理，合在一起概念就太多了：契约、负责方、代理文件、本体约定、产生者、锚点……每多一个概念，就多一份维护，也多一处要人记住的东西。长久使用要的不是功能多，而是**一个思路，新的需求都能放进去，而不必增加新的概念**。

这个思路就是 11-09 晚上开始做的"读和写"。这里把它推到底：

> **xpisode 是一张只追加的读写图。每一次写，都记下是谁写的、读了什么。站点是把物理世界写成流的那个程序；其余一切功能，都是在这张图上读和写的程序。**

核心只负责四样东西，其余都不属于核心：

| 核心 | 是什么 | 为什么只能在核心 |
| --- | --- | --- |
| **物** | 只写一次的文件：Episode、运行的输出、判断、计划、任务的各个版本 | 所有程序都从这里读，必须只有一种存法 |
| **写记录** | 每一次写：谁、何时、读了什么、写了什么 | 血缘、信任、复用、合并都靠它 |
| **站点** | 把设备的流写成 Episode 的那个程序，外加它的契约 | 只有它摸得到实时和硬件 |
| **写入的通知** | 一个按到达顺序排列的"刚写了什么"的流 | 让其他程序能对写入作出反应，而不必各自轮询 |

**判断任何一个新需求，只问一句：它是哪个程序，读什么，写什么？** 能这样说清的，就不需要动核心。

### 0.1 用这一句，回头看今天的所有需求

| 需求 | 是哪个程序 | 读什么 | 写什么 |
| --- | --- | --- | --- |
| 采集 | 站点 | 清单、锁文件、代码、设备的流、计划的这一行 | Episode |
| 判断 | 一个人 | 一条 Episode、任务版本 | 一条判断 |
| 快速质检（小循环） | 快检程序，监听写入的通知 | 刚写的 Episode、任务的成功标准 | 一次运行：规则和 VLM 的结果 |
| 针对性采集（大循环） | 一个生成计划的程序 | 评测的 Episode 和判断 | 一份新的示教计划 |
| FLORA | 一个程序 | 若干 Episode | 一次运行 |
| 建数据集 | 一个人或程序 | Episode，**以及它依据的那些判断** | 数据集 |
| 导出、训练 | 一个程序 | 数据集、代码、配方、基模 | checkpoint |
| 评测 | 站点，加上候选客户端 | 计划、checkpoint 或 API | Episode；之后人写判断 |
| 溯源 | 任何人 | 一个物 | 不写：沿着"读了什么"往回走 |
| 公平比较 | 任何人 | 两个候选的读写图 | 两张图的差：共同读了什么，各自读了什么 |
| 看数据的代理文件 | 一个程序，监听写入的通知 | 刚写的 Episode | 视频文件 |
| 同步 OSS | 一个程序，监听写入的通知 | 新写的物 | 远端的副本 |
| 新本体（逐际） | 站点，换了设备 | 新设备的流 | Episode |
| UMI / Ego | 一个导入程序 | 外部的视频和管线的输出 | Episode |
| 站点体检 | 站点 | 一段固定的轨迹 | Episode，作为"站点此刻状态"的记录 |

后面各节里的新概念，在这张图里都不是新概念：

| 后面提出的 | 在读写图里其实是 |
| --- | --- |
| 契约 | 一次写声明了要读什么，读不到就不写。0 帧的录制，是一次"声明读了相机、其实没读到"的写 |
| 负责方 | 站点这一刻的写是记在谁名下的，也就是写记录里的"谁" |
| 判断者由计划指定 | 计划写明它读谁的判断 |
| 产生者（导入） | 写出这条 Episode 的那次运行：可以是站点，也可以是导入程序 |
| 本体约定 | 站点启动时读的一份文件，按哈希引用 |
| 代理文件、快检、同步 | 监听写入通知、读一个物、写另一个物的程序 |
| 复用而不重算 | 同样的读、同样的代码已经写过，就直接用那次写的结果 |
| 锚点 | 两批评测都读了同一个候选 |
| 开放标注的管理 | 见第 0.3 节 |

### 0.2 这个思路要求的、今天还没有的

我对照 `launch` 分支查过，读写的骨架已经在了，但有五处断口。前三处会改变录下来的事实，必须在正式采集之前补上：

| # | 断口 | 现在 | 要改成 |
| --- | --- | --- | --- |
| 1 | **站点这个最大的写者，自己没有写记录** | Episode 头里有 `run_id`，但 `store/` 里一条运行记录都没有，血缘的根是空的 | 站点运行结束时写出运行记录（中途崩溃由恢复补写）：读了什么（已有，在头里），写了哪些 Episode |
| 2 | **写记录里的"谁"不可靠** | 按计划录的 Episode、评测台写的判断，"谁"都记成 `plan` | 永远是人或程序的名字；经由哪个入口另记 |
| 3 | **声明读了却没读到，照样写** | 必需的流不在时照样录，封存为正常结束 | 契约（第 5.3 节）：读不到就不写，中途断了就中止 |
| 4 | **数据集没有记下它依据的判断** | 选成员时排除了判为"不要"的，但运行记录的 `read` 里只有 Episode | `read` 里也列出用到的判断。这样溯源能走到"谁说这条能用"，换一批判断就是一个新的数据集 |
| 5 | **没有写入的通知** | 播报程序轮询站点状态，OSS 推送每 300 秒扫一遍，快检和代理文件又要各写一套 | 核心提供一个"刚写了什么"的流：本机从索引里读，HTTP API 也给一份。所有反应式的程序都读它 |

**2026-11-11：** 五处都已补上（站点的运行记录；`who` 和 `via`；契约和 `blocking`；数据集的 `read` 里列出判断；`/api/v1/writes`）。下面说的统一视图还没做。

还有一处是表达上的：七种记录各有各的写法，比如判断用 `about`，计划用 `revised_by`，运行用 `who` 和 `read`。**【改】** 文件格式这次不改，但 `xpisode_format` 提供一个统一的视图：每一条记录都能读成"谁、何时、读了什么、写了什么"。溯源、通知、同步、信任都只认这个视图。将来真要统一文件格式，也只是改这一个地方。

### 0.3 开放标注怎么管：信任在读的一边

你担心开放标注会让管理难度骤升。在读写图里，这件事可以倒过来看：

- **写的一边不设门槛。** 任何有名字的人或程序都可以写判断，每一条都署名、只追加，不会覆盖别人的。
- **信任在读的一边。** 建数据集、推进计划、出评测结果的那个程序，自己决定读谁的判断，并把这个选择写进自己的 `read`。比如"只读任务负责人和评测员的判断"，或者"读 FLORA 0.3 版，但人的判断优先"。

这样，开放不会让任何已有的结果变脏：已有的数据集读的是哪些判断，记录里写得清清楚楚，新来的判断不会悄悄混进去。管理也不再是"审批每一条写入"，而是"每个用数据的人声明自己信谁"。这个规则现在就能定，开放以后不用改。

### 0.4 这个思路不管的

- **实时控制。** 设备、客户端、控制组、租约，走的是设备协议和环境协议。它们产生的流写进 Episode，但控制本身不是读写图上的程序。
- **对内容的判断。** 读写图记下谁说了什么，但不替任何人说这条数据好不好。
- **界面。** 面板只是读写图的一个读者，外加给人写判断、写计划的一个入口。

### 0.5 用它来检验后面每一节

后面各节保留了下来，但都应当读作这个思路的推论。今后的任何提议，先用三句话检验：

1. 它是哪个程序，读什么，写什么？
2. 它需要核心多出一种东西吗？如果需要，为什么不能是一次普通的写？
3. 它写下的记录，能让下一个人沿着"读了什么"找回来吗？

三句都答得上，才往下做。

## 1. 这个系统是什么

xpisode 让一组真实的机器人硬件成为可以共用的研究设备：很多人、很多方法、很多 agent 在同一个站点上采集、运行策略、评测，并且事后能说清每个结果是怎么来的。

它要同时对四种人成立：

| 谁 | 处境 | 系统欠他什么 |
| --- | --- | --- |
| 操作员 | 手在主臂上，眼睛看机械臂，不看屏幕 | 录下来的就是能用的；不能用时当场知道 |
| 研究员、agent | 不在现场，隔着数据和 API | 每条数据、每个结果都能追到来源；别人的操作不会悄悄影响自己 |
| 管理员 | 管机器、磁盘、同步 | 系统说得清自己现在的状态和原因 |
| 训练服务器 | 没有站点，没有面板 | 只靠一个库和一个目录就能读、能写 |

它不做的事：排名和统计、判断数据好坏、训练和调度、替第三方写适配、运动学、标定。

衡量这份设计的五个标准，每一节都要经得起它们：

| 标准 | 具体是说 |
| --- | --- |
| 开放 | 外面的人、外面的机器人、外面的方法和数据，不经过我们就能接进来 |
| 包容 | 几乎任何研究方式都能做：示教、评测、无人值守的强化学习、离线研究、外来数据 |
| 负担小 | 每个人只学他用到的那部分；接一个方法的代价接近零 |
| 积累 | 做过的事（数据、导出、checkpoint、评测、接入代码）以后还能用，而不是重做 |
| 可信 | 录下来的就是能用的，每个结果都能追到来源 |

第一版只按"可信"想，后四条在第 8 节补上。它们不只是加功能：第 6 节的负责方和判断原本会挡住无人值守的研究，已经按这五条改过。

## 2. 从哪里出发

2026-11-10，站点在开机 34 秒时启动，约 5 秒后系统时钟被对时服务回拨了 11 秒。三台相机因时间戳倒退先后进入故障，此后不再恢复。站点仍然显示就绪。操作员又录了十几条，每条都没有一帧图像，都封存为"正常结束"，采集计划照常推进。提醒程序没有运行。同一天的 136 条录制没有一条被人判断过，其中 129 条的操作者记成了 `plan`。

这里的每一步单独看都符合当时的设计：故障不自动恢复，缺流只记录不判断，提醒在核心之外，没人判断就算要。合在一起，系统在没有相机的情况下产出了"完成"的数据。所以问题不在某一处实现，而在四个设计层面的缺口：

1. **两条原则之间没有界线。** "站点对自己的鲁棒性负责"和"只记录事实、不下结论"都对，但没说清站点自己声明的契约属于哪一边。结果契约也被当成了"事实"，记一笔了事。
2. **默认值全部放行。** 没信号就当没事，没判断就当要，有录制就当完成。
3. **状态是事件，不是事实。** 就绪算一次就一直成立；故障进去就出不来；时钟换算测一次就假定永远对。
4. **会变的工具握着不该它握的东西。** 采集计划走到哪一行、评测时启动哪个候选、操作者叫什么，都在面板进程里；而面板被定义为"随时可以重写"。

下面的设计围绕这四点重新组织。

## 3. 原则

1. **站点执行自己声明的契约；不评价内容。**
   契约是站点清单、协议和计划里写明的东西：哪些流必须在、时间不倒退、谁在负责、这一行要录什么。契约在动作发生时执行：不满足就不开始，中途破了就中止。内容好不好（动作流不流畅、任务成没成、哪个方法更强）永远在外部。检验：契约的每一条都能由站点自己、不看数据内容就判定。

2. **没有依据就不放行。**
   任何"通过"都要有正面的依据：流是活的，人按了键，记录写完了。缺依据时的默认结果是拦住，并说明缺什么。

3. **状态由当前的数据算出。**
   就绪、健康、进度都是函数，输入变了结果就变，没有只进不出的状态。

4. **事实只由对它负责的一方写。**
   实时的事实由中心写，现场流程的事实由站点进程写，事后的事实由有名字的运行写。界面不持有状态，重启界面不改变任何事实。

5. **只写一次，可以合并。**
   写完的东西不再改；更正、撤回、判断都是新的记录。几台机器各写各的，取并集就是合并。

6. **标准是唯一的入口。**
   设备、策略、数据使用者都通过公开的协议和格式接入，我们自己的也一样。核心里不出现第三方的名字。

7. **和已有的生态对接一次，而不是每个方法对接一次。**
   研究者已经在用的东西（LeRobot 的数据格式、openpi 式的推理服务、ROS 2 的驱动）由我们写一座桥，所有方法共用。这和第 6 条不冲突：桥对接的是另一个标准，不是某一个第三方项目。

8. **每个人只学他用到的那部分。**
   只要数据的人，只需要一个数据集 id 和一个库；只跑策略的人，只需要一个推理服务。负责方、计划、契约是站点的事，不该出现在研究者面前。

9. **做过的事可以被找到、被复用。**
   同样的输入、同样的代码再算一次之前，先能查到上一次的结果。

10. **先在真机上证明，再冻结。**
    涉及物理行为的设计要有实测；格式在整条流程真实走通之后才冻结。

### 维护成本：先于任何新功能

做一个新东西不难，难的是之后一直养着它。这份文档里每一项提议都要先过这一关。

**这个项目的维护成本已经可以量出来：**

| 来源 | 实测（2026-10-12 至 11-10） |
| --- | --- |
| 做了又拆 | Benchmark 一类功能在一周内建成，又拆掉了 5284 行；衍生层建成约 1700 行，第二天拆掉 1433 行 |
| 接口变得太快 | 格式和协议的源文件 5 周内改了 55 次，本周 15 次 |
| 依赖面太宽 | 11 个方法仓库各写 700–2900 行，碰到格式、协议、`frames` 的组装、HTTP API；每个仓库都有 2–5 个只为跟上核心变化的提交 |
| 真相分散 | ADR、规范、代码、METHODS.md、skill 各有一份，接受一天就互相不一致 |
| 回归只在真机上暴露 | 0 帧录制在单元测试里看不出来 |
| 知识留在会话里 | 很多"为什么"只在 agent 的对话和记忆里，仓库里没有 |

**大致的规律：** 维护成本 ≈ 每个接口的"依赖它的地方 × 它变化的频率 × 每次跟改的代价"之和，加上"我们拥有的东西 × 它所处环境变化的速度"。要压低它，只有三件事：接口少、窄、变得慢；拥有的东西少；跟改便宜。

由此定八条规则：

| # | 规则 | 怎么执行 |
| --- | --- | --- |
| M1 | **没有当前用户就不做。** | 进核心要有两个真实的用途，第一个用途先在外部实现。生态包也一样：一座桥至少有两个方法在用才建。"以后会有人用"不算 |
| M2 | **每样东西有主人，也有删除条件。** | 主人写在这份文档里。删除条件写成"多久没人用"，用记录里的事实来量，不靠印象 |
| M3 | **对外承诺的面要窄、变得慢；内部可以宽、变得快。** | 对外只承诺六样：Episode 格式、设备协议、环境协议、`store/` 的规则和七种记录、读取接口、HTTP API 的一个版本。面板、脚本、内部模块都不承诺，外面不许依赖 |
| M4 | **拥有的越少越好。** | 能用配置就不写代码，能不 fork 就不 fork，能提到上游就提到上游。方法接入的理想形态是一份配置加上游的某个提交 |
| M5 | **跟改要便宜，最好由 agent 自动完成。** | 规范从代码生成（JSON Schema 已经这样做了）。每个依赖方都有一条静态检查命令；核心一变，跑一遍就知道哪些仓库要改，并由 agent 批量跟改 |
| M6 | **一件事只有一个真相。** | 设计只在这份文档里；字段只在规范里；方法的进度只在运行记录里。METHODS.md 改为从运行记录生成，或者删掉 |
| M7 | **难反悔的慢慢定，好反悔的快快做。** | 慢：格式、数据、物理布置、对外接口。快：面板、脚本、实验 |
| M8 | **自由键要有命名空间。** | 记录允许额外的键，但名字没有规定，以后要标准化某个键时会撞上已有的用法。规定：自由键以 `x_` 开头，后接主人的名字；标准键永远不以 `x_` 开头 |
| M9 | **规则卡。** | 每种角色要遵守的规则，都能写在一张卡片上，新人五分钟能读完（第 7.6 节）。新功能如果要让用户多记一条规则，就要说明为什么不能交给工具自动处理。卡片就是上手说明；卡片写不清楚，说明设计还没想清楚 |

### 没有指标时怎么把关：这个项目反复出现的七种问题

很多决定给不出数字。这时用经验把关：下面七种问题在过去一个月里都真实发生过，每一种都已经变成了这份文档里的一条规则。任何新的提议，先对着这张表问一遍"会不会又是这一种"。是的话，要写明为什么这次可以。

| 问题 | 发生过的例子 | 变成了哪条规则 |
| --- | --- | --- |
| 在有用户之前就造出来 | Benchmark 建了又拆，5284 行；衍生层建了约 1700 行，第二天拆掉 1433 行 | M1 |
| 失败时放行 | 相机 0 帧的录制封存为正常结束；没人判断就算要；计划照常推进 | 原则 2 |
| 同一套语义写了好几遍 | 9 个方法各自用 `frames` 拼样本；相机适配器自己换算时钟 | 第 8.3 节：语义只在腰上 |
| 状态放在会变的地方 | 评测流程在面板进程里；就绪只在启动时算一次 | 原则 3、4 |
| 有人依赖之后接口还在变 | 格式和协议 5 周改了 55 次，每个方法仓库都在跟改 | M3 |
| 在人等着的时候才算 | 判断页每看一条新录制就转码 9 路视频 | 第 7.5 节 |
| 真相不止一处 | ADR、规范、代码、METHODS.md 接受一天就对不上 | M6 |

这张表是活的。以后每出一次事故、每拆一次刚建好的东西，就回来加一行：发生了什么，变成了哪条规则，怎样检查。这样，经验不必每次都由人重新讲一遍，agent 读这份文档就能用上。

**HTTP API 也是接口。** 今天 add-method skill、abc 的导出器、starVLA 的扫描脚本都在调它，可它没有版本号。**【改】** 加上 `/api/v1/` 前缀，冻结时一起冻结；面板内部用的接口另放一处，不承诺。（已做：面板自己的在 `/api/panel/`，旧的 `/api/` 路径暂作过时的别名。）

**测试的分工：** 验收只认真机，这一条不变。但回归不能只靠真机：核心的契约（停帧、时间倒退、进程消失）用会出故障的假设备写成自动测试，每次改动都跑。这些测试检查的是核心自己的行为，不用来验收方法和设备。每次开工的站点体检（回放一段固定的轨迹，和上一次对比）则在真机上检查站点本身有没有漂移。

## 4. 四层

系统分四层，每层有自己的保证和自己的失败后果。一个功能放在哪一层，看它需要哪种保证。

| 层 | 是什么 | 保证 | 坏了会怎样 |
| --- | --- | --- | --- |
| 实时层 | 中心、设备进程、客户端进程 | 安全、时序、契约 | 机械臂停住，录制中止 |
| 现场层 | 站点进程里的流程：负责方、计划游标、判断、候选的启停 **【改】** | 现场每一步都有人负责，都留下事实 | 站点不就绪，不能录 |
| 记录层 | `store/` 和读写它的库 | 不变、可追溯、可合并 | 不会坏：只追加 |
| 界面层 | 面板、HTTP API、脚本、提醒、报告 | 没有保证，随时可以重写 | 看不到，但什么都不丢 |

**【改】** 现场层是新划出来的。今天这些流程在面板进程里（`web/evaluation.py` 启动候选、到时停止录制、设置录制的上下文），面板一重启，正在进行的评测就没人管了，而且由它写进 Episode 头的东西没有可靠的来源。现场层搬进 `xpisode run` 的站点进程（Python 一侧，不进 Rust 的控制线程），面板和实体按钮都只是它的入口。

## 5. 实时层

### 5.1 进程和控制

这部分经过了真机检验，保持不变：

- 一个站点一个**中心**（Rust）：控制和录制在同一个进程，中间是有界队列，互不等待。其余都是**服务**：设备进程和客户端进程，各自独立，经共享内存通信。
- 设备通过设备协议接入，站点不认识设备类型。控制权和看门狗合并为**租约**，由设备端在最后一跳执行；租约属于一次站点运行。
- 所有控制源都是环境协议的客户端，包括遥操作。站点只做仲裁、调度、发令和记录。**时钟和主循环属于站点**：策略慢了或崩了，站点照自己的节奏执行或保持，断档超过阈值就释放租约。
- 控制组的 `holder` 是它的归属；切换是站点的操作，客户端不能自己夺取。非持有者的动作照样记录，不执行。
- 设备、客户端的每条依赖都有存活信号和对方消失时的安全状态。

### 5.2 时间

一个时钟：站点主机的单调时钟。每条样本带这个时钟的时间戳，流声明它代表采集、接收还是产生的时刻。

**【改】** 三条新规则：

1. **系统时钟不进入任何时间戳的计算。** 它会被回拨。它只用来给人看日期。
2. **设备时钟到主机时钟的换算由设备 SDK 做，不由适配器做。** 适配器只交出设备自己的时间和 SDK 给它的接收时刻。换算是容易写错的部分，写错一次就是今天的事故，所以只写一份，放在标准的参考实现里。
3. **单个倒退的样本丢弃并计数；持续倒退才是故障。**

### 5.3 契约和健康

**【改】** 站点清单声明"一次有效的录制需要什么"：

```toml
[[require]]
stream = "/cam_head/frame"
max_gap_ms = 200          # 超过这个间隔没有样本，就算不在

[[require]]
client = "announcer"      # 提醒程序必须在场
```

内置的几项不用写：控制时钟在运行、有负责方（第 6.1 节）、数据盘余量高于下限、没有上一条未封存的录制。计划可以再加自己的要求，例如"这一行开始时 instruction 不为空""候选已经连上"。

中心持续计算每一项现在是否满足。站点状态里有一个列表 `blocking`：当前不满足的每一项，以及原因。**它是唯一的来源**，下面这些都从它导出：

| 导出的东西 | 规则 |
| --- | --- |
| `ready` | `blocking` 为空 |
| 开始录制 | `ready` 才开始；否则拒绝，把 `blocking` 写进 `operator.input.refused` |
| 录制中 | 任何一项破了，立即中止，`aborted`，原因就是那一项 |
| 提醒 | `blocking` 每次变化是一条站点事件；提醒程序只读这个 |
| 面板 | 显示同一个列表 |

这样"为什么不能录"在任何入口都有同一个答案。

由此，`termination = finished` 就意味着契约自始至终成立。规范里已有"完整的 Episode"这个定义，它从事后的标注变成站点的保证，Episode 格式不用改。

### 5.4 故障之后

**【改】** 故障不再是终态，但恢复方式按设备分：

- **只发布流的设备（相机等）**：设备宿主带退避地自动重试。恢复后健康值自己变回来。
- **有端点的设备（机械臂等）**：不自动恢复。负责的人用站点操作 `recover <设备>` 让它重新来，不必重启整个站点。

理由不变：机械臂出问题后不该无人监督地重来。但这个理由不适用于相机，也不该要求用重启整个站点来恢复一台设备。

### 5.5 启动前检查

**【改】** `xpisode run` 开始时检查主机，不通过就不启动，并说明怎么修：系统时钟已同步、数据盘余量、未恢复的录制（先恢复，恢复不了的移入隔离目录）、CAN 接口、相机权限、共享内存大小。

站点由操作员启动。**【你定】** 今天站点在开机 34 秒时就起来了，原因没有查清；如果是有意设的自启，按这份设计应当去掉。

### 5.6 站点日志

**【改】** 今天，录制之外发生的事没有任何持久的记录：相机什么时候故障、哪次按键被拒绝、站点什么时候重启，只在面板上闪过。相机的日志文件是空的。

每次站点运行都是一次**运行**，有自己的运行记录，并写出一个站点日志：不含图像的一个小 MCAP，从启动写到关闭，内容是站点事件、控制事件、设备状态、`blocking` 的变化、负责方的变化。Episode 里照旧包含它自己那一段的这些流。

用处：两条录制之间出了什么事有据可查；一致性报告可以比较两次站点运行；"这台站点今天怎么了"不需要有人恰好在看面板。

## 6. 现场层

### 6.1 负责方

**【改】** 站点任何时刻至多有一个**负责方**：对站点此刻发生的事负责的那个名字。上岗和离岗是站点操作，记为站点事件。没有负责方是一项 `blocking`。

负责方通常是一个人。为了不挡住无人值守的研究（夜间的强化学习、带自动复位的长时间评测），它也可以是一个程序，但要满足两条：站点清单允许无人值守，并写明允许哪些程序；程序上岗时声明自己会跑多久，到时自动离岗。程序负责期间，契约照样执行，任何一项破了就停下，等人来。**【你定】** 这台站点是否允许无人值守。

这一个概念同时解决三件事：

- **身份。** 录制、判断、按键都记在负责方名下。`who` 永远是人或程序的名字；经由哪个入口（按钮、面板、API、计划）记在另一个字段 `via`。今天按计划录的 Episode 操作者是 `plan`，这种写法不再可能。
- **占用。** "站点现在谁在用"有了答案，面板和 API 都能看到。
- **授权。** 会让机械臂动或改变录制的操作，只有负责方能发起。别人或 agent 要做，由负责方按名字授权，授权也是站点事件，离岗即失效。

没有密码和令牌。威胁模型和设备一侧相同：防意外，不防恶意；能登录站点机的人本来就能做任何事。面板仍然只监听本机。

研究者不需要知道负责方。他通过 API 或 agent 提交计划和候选，由负责方决定什么时候跑。

### 6.2 回路

操作员的工作是一个回路，站点进程把它作为一个状态机来执行：

```text
不就绪(原因) ⇄ 就绪 → 录制中 → 待判断 → 就绪
```

**【改】** 输入映射按阶段生效：同一个按钮在"就绪"时是开始，在"录制中"是结束，在"待判断"是判断。具体哪个键做什么写在站点清单里。

**判断并入"下一条"这个动作。** 按计划采集时：

- 示教：结束后，"下一条"就是对上一条的判断 `keep: true`；另有一个"重录"键：这条录制无效，在本机直接删掉、不上传，这一行重做（第 7.6 节）。两种都只按一次，不比今天多一步。
- 评测：成败不能默认，必须明确给出成功、失败或重做，然后才能开始下一行。
- 不按计划的自由录制没有"待判断"这一步，录完就是没判断。

**【改】** 计划写明谁来判断：默认是负责方；也可以指定一个程序（自动的成功检测、奖励模型），这时"待判断"由那个程序在限定时间内写出判断，判断者记为程序的名字。这是无人值守的评测和强化学习能用计划的前提。程序的判断和人的判断并存，各自署名；对同一条 Episode，人后来给出的判断照常成为当前判断。

这样，没判断不再悄悄等于要：要，是一次有名有姓有时间的动作。"没判断"是一个单独的、看得见的状态，建数据集时默认不选。**【改】**

### 6.3 计划

计划是事先写好的一张清单，每行写明这一次录什么：遥操作，或某个候选；哪种布局；这一行的 prompt。示教计划和评测计划是同一种东西。顺序事先固定，可以审计；提前结束就是删掉没做的行。

**【改】** 计划的游标属于站点进程：`open plan` 是站点操作，站点进程从 `store/` 里的计划、录制和判断算出下一行，启动和停止候选的进程，到时限结束试验。面板只显示。

**【改】** 一行已完成，当且仅当有一条记着这一行的、**正常结束的** Episode，并且计划指定的判断者给出的当前判断是 `keep: true`。原来的规则是"判断不是 `keep: false`"，于是没人判断时任何录制都算完成。（已改。）

评测台不向操作员显示候选的名称。布局是某条 Episode 的某一刻，复位时和实时画面并排显示。评测是一种采集，不产生排行；计划页只显示进度和原始计数。

### 6.4 提醒

怎么提醒（语音、灯、声音）不是核心的事，由清单里的一个普通客户端来做。核心保证两件事：这个客户端在清单里写成必需时，它不在站点就不就绪；它要的信息只有 `blocking` 的变化和录制的开始、结束、中止，都是站点事件。

## 7. 记录层

### 7.1 存储

数据根目录分两部分：`store/` 只写一次、可以同步、多台机器共用；`local/` 是本机的索引、缓存、日志和进行中的状态，可以删。备份、同步、交给别人只需要 `store/`。

- id 是时间加 48 位随机数；路径由 id 的随机部分决定，不含时间、站点、任务、人。
- 每个文件先写临时名字再改名。一次运行的输出，在它的运行记录出现之前都当作不存在。
- 合并就是取并集；同一路径出现两份不同的内容是违约，同步工具报错停下。

**【改】** 明确一条：**任何机器只往自己本地的 `store/` 里写，再由同步工具推出去。** 训练服务器把桶挂载成只读的数据根目录来读，不往挂载点里写：对象存储上的改名不是原子的，"先写临时名字再改名"在那里不成立。

### 7.2 七种记录

核心认识七种记录，各有固定的"当前"规则。除此之外的一切（导出、训练、同步、标定更正、模型打分、清理）都是带自由键的**运行**，核心不区分它们的种类。

| 记录 | 是什么 | "当前" |
| --- | --- | --- |
| Episode | 站点录下的一段 | 不变 |
| 运行 | 谁、何时、读了什么、写了什么 | 不变；可被另一次运行撤回 |
| 判断 | 一个人对一条 Episode 或其中一段的意见 | 对同一对象，最晚的那个 |
| 任务 | 说明、成功标准、默认 instruction | 同名的最晚版本 |
| 计划 | 清单及其每次修订 | 最晚的修订；做完的行不能改 |
| 数据集 | 冻结的成员清单，带命名的部分和切分的 seed | 不变 |
| 模型 | 机器人模型目录，按内容哈希存 | 不变 |

**【改】** 这是对"不维护分类学"的更正。那个说法的用意是对的：不为导出器、策略、checkpoint 这些随研究方式变化的东西设类型。但核心确实认识上面七种，说成"没有分类"，以后每加一种都要争论算不算破例。老实的规则是：这七种是核心的词汇，加第八种要改这份文档。

三条贯穿始终的规则：

- **引用**是带前缀的字符串（`episode:`、`run:`、`sha256:`、`git:` 等），前缀开放，读不懂的原样显示。
- **切分由数据集决定。** 两个方法用同一个数据集，用的就是同一份训练数据和同一份留出数据。
- **程序的输出永远以程序的名字记录。** 它只在计划明确指定它为判断者时推动计划（第 6.2 节），从不冒充人的判断，也不参与核心的其他计算。

### 7.3 血缘

每条 Episode 的头里记着站点读了什么（清单、锁文件、各个包的提交）和每个客户端读了什么（checkpoint、代码）；每次运行记着自己读了什么。于是从一次评测的结果可以一路走回训练、导出、数据集、采集时的站点。

血缘只和声明一样完整，缺的地方显示为缺口。这一条宽容只适用于对来源的声明，不适用于第 5.3 节的契约。

**【改】** 沿着引用往回走的那一步（给一个引用，列出它的全部祖先和缺口）放进 `xpisode_format`，因为它定义了"声明得够不够"。两条血缘的对比、报告仍在外部。

### 7.4 容量

**【改】** 容量是设计的一部分，不只是运维的事。今天的实测：三台相机每条流是原始图像加 zstd，写入约 160 GB/h；上传约 54 GB/h；盘余 1.2 TB。

按这组数字，一天采集 H 小时，需要 H × 106 GB 的本地缓冲，和 H × 3 小时的上传时间。一天 6 小时要传 18 小时，还有余地；8 小时要传将近 24 小时，就没有余地了。这只是一天的数字，要再测。

所以定三条：

1. **站点知道自己还能录多久**：余量除以最近的写入速率。它显示在状态里，低于下限是一项 `blocking`。
2. **只清理已经在远端校验过的对象**，清理本身留一条运行记录。
3. **图像编码按实测选。** 实测（2026-11-10，一条 44 秒的录制）：彩色已经是每帧独立的 FFV1，每帧约 241 KB（原始 922 KB，压缩到约四分之一）；左右红外是原始像素加 zstd，每帧各约 163 KB（原始 307 KB，只压到约一半）。**红外占了相机数据的 57%。** 格式里的 FFV1 原先只允许三通道彩色，单通道的红外用不上它（dev 上已允许灰度 FFV1，正式站点待你确认）。**【你定】** 红外是否保留；保留的话，是否给格式加一种适合单通道图像的无损编码（FFV1 本身支持灰度），这要在冻结前定。

### 7.5 看数据要快：代理文件

**实测（2026-11-10，站点机）：** 判断页打开一条还没看过的录制（2.1 GB，约 44 秒），

| 步骤 | 耗时 |
| --- | --- |
| 录制列表、录制详情、判断 | 合计不到 0.1 秒 |
| 读完整个 MCAP | 0.8 秒 |
| 生成 Rerun 视图：9 路 AV1 视频（3 台相机 × 彩色和左右红外），各约 7 秒 CPU，并行 | **16.6 秒后才出第一个字节** |
| 已经生成过的视图 | 0.03 秒 |

之后浏览器还要启动 Rerun 的 wasm 查看器，并解码 9 路视频，这部分没有测。耗时和录制时长成正比，2 分钟的录制大约要 45 秒。按 150 条算，光是等待就要 40 分钟以上。

**根本原因不在代码慢，而在两个架构选择：**

1. **视图是在人要看的那一刻才算的。** 每看一条新录制，就从无损原始数据重新转码一次，而且算在人的等待时间里。可是要看哪些录制是事先知道的：判断页的队列就是"还没判断的录制"，按顺序排好了。
2. **只有一种视图，而且是最重的那种。** 判断只需要扫一眼：成没成，有没有问题。可它加载的是细看用的全量视图：9 路视频、所有曲线、三维场景、机器人模型。其中 6 路红外占了三分之二的转码时间，判断时几乎用不上。

**影视后期早就有现成的做法：代理文件。** 剪辑时用低分辨率的代理，最终输出时才回到原片。这里也一样：

- **原始的 Episode 是母版**，无损，只写一次，训练和细看用它。
- **代理**是一次运行的产出：每台相机一个彩色的视频文件，分辨率和码率适合浏览器原生播放，再加一小份曲线和事件。它可以随时删掉重建。
- **在录制封存后、后台生成，不在人看的时候生成。** 优先生成判断队列里排在前面的，判断某一条时先把下一条准备好。在站点机上以低优先级运行；中心的控制线程是实时调度，不受影响，但要实测控制节拍的抖动。
- **判断页用浏览器原生的视频播放**，三路同步，下面一条时间轴标出开始、切换、接管和快检的结果，用键盘判断。点"细看"时才打开 Rerun 的全量视图和时间窗口。

代理也是一种派生，所以按第 8.3 节的规则，它是边，不是腰。它还有一个附带的好处：代理推到远端以后，在 OSS 上浏览数据的人也能很快看到；如果某个方法训练时恰好要同样规格的压缩视频，可以直接复用这份代理，不用再转一次。这一点只有规格对得上才成立，不预设。

**性能的目标写成数字，作为验收标准：**

| 指标 | 目标 |
| --- | --- |
| 判断页从点开到第一帧 | p95 < 1 秒 |
| 判断后切到下一条 | p95 < 0.5 秒 |
| 封存到代理可用 | 不超过录制时长的一半 |
| 后台生成代理时，控制节拍的抖动 | 和不生成时相比，没有可见的变化 |
| 细看（Rerun 全量视图），第一次打开 | 不超过今天的一半 |

**性能优化可以交给 agent，架构不能。** 指标一旦写成数字、并配上一个基准测试，agent 就能自己反复改、反复量，直到达标。基准测试用真实录下的 Episode 作样本（`repos/xpisode/scripts/bench_episode_images.py` 已经是这种思路），每次改动都在 CI 里跑，退化了就报出来。人要做的是这一节前面那部分：认出"在看的时候才算"和"只有一种视图"是根因，而不是去调编码器的参数。

更一般地说：在一个由 agent 驱动开发的项目里，人的判断要尽量写成 agent 能执行的东西。性能写成指标和基准，边界写成 import 检查（面板的代码不许被任何包导入，方法仓库只许用对外承诺的接口），规则写成静态检查（第 3 节的 M5）。写不成检查的，才留在这份文档里，靠人来把关。

### 7.6 多台采集机，一个 OSS，以及删除

常见的情况是：几台采集机，各接一台或几台站点，共用一个 OSS；训练服务器读 OSS。下面的规则就是为这种情况写的，一台机器、没有 OSS 时也照样成立。

**一条拓扑：只有中心，没有机器之间的连接。** 每台机器（采集机、训练服务器）只和中心 OSS 打交道，从不连接其他机器，也不假定其他机器在线。机器之间要知道的一切，都经过中心。

**两条同步规则：**

1. **小东西上推也下拉，大东西只上推。** 小东西是判断、计划、任务、运行记录、边车和缩略图；大东西是录制文件和运行写出的大文件（导出、checkpoint）。每台机器把自己写的小东西推到中心，再从中心拉回别人写的，所以研究员在任何一台机器上建的计划和数据集，过一个同步周期就出现在其他机器上。大东西只在需要时才从中心拉下来。
2. **只写本机，再推上去。** 任何机器都不直接写 OSS 的挂载点。

**计划默认绑定一台站点**（计划的 `station` 字段）。这样采集进度只取决于这台机器自己写的录制和判断，不需要等其他机器同步，也不会两台机器同时录同一行。跨机器的只有读：建数据集、看判断、评测结果。

所有东西只写一次、id 随机，所以几台机器的数据取并集就合并好了，不会冲突。两台机器同时修订同一份计划，会出现一个看得见的分叉（第 7.2 节的 `replaces`），由人来合。

**删除，最常见的是采集时的错录。** 操作员按计划采集，录下来的这一条不符合计划的要求：摆放不对、开始早了、中途被打断。这不是一次失败的尝试，而是一条无效的录制。离源头最近的时候直接删掉，最简单：

- **按计划录的录制，先判断再上传。** 采集员按"要"，它才进入推送队列；按"重录"，它就在本机直接删掉，从没离开过这台机器，其他机器和 OSS 都不知道它存在过。站点的运行记录只记一个数：这次运行删掉了几条，用于统计废弃率，不记内容。
- **不按计划的自由录制**，录完后等一段时间（默认 10 分钟）再上传，在这之前可以直接删。
- **"重录"和"失败"不是一回事。** 尝试做了、但没做成，是一条有价值的失败数据（质量评估和 FLORA 都需要它），要按"要"，并判为失败。只有录制本身无效时才按"重录"。
- **已经上传的录制**极少需要删（隐私、事后才发现的误录）。由管理员用"删除"命令处理：先在中心写一条删除记录，并删掉中心的副本；各机器下次从中心同步时看到这条记录，各自删掉本机的副本；执行前列出受影响的数据集。
- **自动清理**和删除是两回事：本机空间不够时，工具只清掉已经在 OSS 上校验过、且不属于在用数据集的录制，永远不会删掉最后一份。用户不需要知道它。

**几条为多台机器加的约定：**

- **站点名在所有机器之间唯一。** 管理员在加机器时定好。
- **人名从一张共享的名单里选**，名单是一个小东西，随其他小东西同步。采集员在面板上选自己的名字，不用每次手打，避免同一个人在不同机器上有不同的写法。名单上没有的名字，可以当场加。
- **采集机用只能新增、不能删除的 OSS 凭证。** 删除只用管理员的凭证。这样，一台采集机出了问题，也删不掉中心的数据。
- **建议给 OSS 的桶打开版本控制，被删的版本保留 30 天**，兜住误删。

**规则卡**（M9）：

| 谁 | 卡片上写的 |
| --- | --- |
| 采集员 | ① 开工前在顶栏选自己的名字。② 录不了时，站点页和语音会说原因。③ 录完一条：做成了或者失败了，都按"要"（失败的要判为失败）；录坏了、不算一次有效的尝试，按"重录"，它会被直接删掉，不会上传。 |
| 研究员和 agent | ① 拿数据：数据集 id 加一条拉取命令。② 训练在服务器本地跑，结果推回 OSS，并声明读了哪个数据集、哪份配方、哪个基模。③ 上真机：客户端声明读了哪个 checkpoint。④ 后判的取代先判的；建数据集时用的是每条录制当前的判断，并会记下来。 |
| 管理员 | ① 数据自动推到 OSS，面板上只显示"还有多少没上传"。② 本机满了会自动清理，永远不删最后一份。③ 已经上传的录制要删除：`删除 <id> --原因 ...`，不能撤回，执行前会列出受影响的数据集。④ 加机器时定好站点名，发给它一份只能新增的 OSS 凭证。 |

## 8. 研究回路和生态

### 8.1 回路

整条回路里每一步谁做、在哪做、留下什么：

| 步骤 | 谁，在哪 | 留下 |
| --- | --- | --- |
| 定任务 | 研究员，面板 | 任务的一个版本 |
| 写示教计划、采集、当场判断 | 操作员，站点 | Episode、判断 |
| 建数据集 | 研究员，面板或 API | 数据集（一次运行） |
| 推到远端 | 管理员或定时，站点机 | 同步运行 |
| 导出、训练 | 研究员或 agent，任何机器 | 导出运行、训练运行、checkpoint |
| 拉回 checkpoint | 站点机 | 本地 `store/` 多了那次运行 |
| 写评测计划 | 研究员 | 计划：候选 × 布局 × 次数，按 seed 打乱 |
| 评测 | 操作员，站点 | Episode、判断 |
| 出结果 | 任何人，任何机器 | 一张每次试验一行的表，全是事实；统计在外部做 |

导出器是策略仓库里的独立程序：读数据集的部分，写结果和运行记录。策略照样板接入环境协议，从站点读 instruction，连接时声明自己读了哪个 checkpoint。核心不运行导出器，不认识策略。

**【改】** 工作区 `pyproject.toml` 里登记的九个导出器删除。站点清单里的 `use = "<包>:<组件>"` 写法不做：清单里完整的启动命令更直白，而且清单的哈希已经记进每条 Episode。

**【改】** 同步工具补上 `pull`（按数据集或运行）和 `verify`。

### 8.2 今天接一个方法要付出什么

11 个方法仓库里，为 xpisode 写的代码共约 1.4 万行，每个 700–2900 行。拆开看，几乎都是重复的：

| 每个方法都在写 | 有几个在写 |
| --- | --- |
| 把 Episode 转成 LeRobot 格式 | 4 个（flex-pi、ODE-POLICY、Phoenix-MWA、RLinf） |
| 转成 HDF5 或 zarr | 5 个（ACT 和 Diffusion Policy 各有一份几乎相同的 `xpisode_adapter`） |
| 时间对齐、切片、读相机 | 9 个文件调用 `frames`，各自组装 |
| 观测转输入、动作块插值、控制权和 RTC 的处理 | 9 个客户端，各自一份 |
| 文档、检查脚本、运行手册 | 几乎每个 |

这些代码散在 30 个仓库的分支里。框架每改一次格式（站点改名、存储布局、运行记录），每个仓库都要跟着改一次；控制器换了，全部 checkpoint 作废。这正是"负担"和"积累"两条标准反面的样子：研究者的注意力花在接口上，而接口代码不能被别人复用。

原因在"只发布标准，不做适配"被读成了"每个方法自己适配"。标准本身没有错，缺的是标准和研究者已有工具之间的那一层。

### 8.3 腰和边：xpisode-format 和桥各自是什么

上一版把"训练用的读取接口"也算作一座桥，这是错的。弄清楚它为什么错，桥和 `xpisode-format` 各自的位置也就清楚了。

**一份录制里有三种东西：**

| 东西 | 例子 | 谁该写它 |
| --- | --- | --- |
| 发生了什么，以及怎么读才对 | 时间戳代表哪个时刻；哪里有缺口；那一刻谁在控制；执行的和提议的动作；一段录制从哪到哪 | `xpisode-format`，只写一份 |
| 别人的习惯 | LeRobot 的列名和视频编码；openpi 的 websocket 消息；ROS 2 的话题 | 桥，薄，可以替换 |
| 研究的选择 | 动作标签用指令还是实测；只要遥操作的片段；多少 Hz；图像多大 | 参数，记在那次运行里，不写死在任何代码里 |

这就是网络里"细腰"的结构：下面是各种设备，上面是各种方法和数据格式，中间只有一个很窄、很稳的腰。**通用性放在腰上，好管理靠边薄。**

- **腰是 `xpisode-format`：** Episode 格式、记录、引用，再加上**按声明的频率和字段读出对齐好的样本**。这一步必须在腰上，因为只有格式知道时间戳的含义、缺口在哪、谁在控制。今天 9 个方法各自调用 `frames` 拼样本，就是同一套语义写了 9 遍，迟早写出 9 种不同的结果。
- **桥是边：** 把腰读出的样本写成 LeRobot 的列，或者把环境协议转成 openpi 的消息。桥里不该有任何关于"发生了什么"的判断，只有翻译。一座桥一旦开始自己判断（比如自己决定动作用实测值、自己过滤掉 `move` 客户端的帧），它就在替所有用它的方法悄悄做研究选择。
- **研究的选择是参数：** 带默认值，写进导出运行或训练运行的 `params`。参数相同的两个结果可以比；不同的，差别在记录里一眼可见。这样研究的自由和结果的可比两头都保住了。

所以，**有了桥之后，`xpisode-format` 的意义正是让桥能够很薄。** 没有腰，每座桥都要自己从 MCAP 重新推出时间和控制的语义，那就不是桥，而是又一份适配。反过来，LeRobot 一类的格式是训练时的视图，不是录制：它表达不了提议和执行的区别、控制权的切换、多种频率的流、无损的红外，也表达不了血缘。两者的关系像相机的 RAW 和 JPEG：RAW 只有一份，JPEG 按需要出，出的时候记下用了什么参数。

**通用和好管理之间的权衡，于是不是一个旋钮，而是按层放置：**

- **腰**要通用：几乎所有研究都要从这里过。它的维护成本靠"小"和"冻结"来压：概念少，改得慢。
- **边**要好管理：每条边只服务一种外部习惯，薄到可以随时删掉重写；它有主人，按 M1 有两个用户才建，只对接外部标准的一个固定版本。
- **研究的选择**不进任何代码，所以既不增加腰的复杂度，也不让边变厚。

按这条重新划分：

| 东西 | 放在哪 | 建造条件 | 今天 |
| --- | --- | --- | --- |
| 对齐好的样本读取 | 腰：`xpisode-format` | 已满足 | 9 个方法在各自组装 `frames` |
| LeRobot 导出 | 边 | 两个以上的方法用 | 4 个，满足 |
| HDF5/zarr 导出 | 边 | 两个以上的方法能共用同一种布局 | 5 个，但布局各不相同，先核对 |
| 推理服务的通用客户端 | 边，`xpisode-env` 的可选部分 | 两个以上的方法有这样的服务 | abc、flex-pi 用 websocket，刚好满足 |
| 动作块的执行、插值、接手后重新规划 | 腰：`xpisode-env` | 已满足 | 9 个客户端各写一份 |
| ROS 2 的桥 | 边 | 第一台要接的 ROS 2 设备 | 没有；看逐际是否走 ROS 2 |
| 仿真设备 | 边 | 一个具体的使用者 | 没有，不建 |

最后一点：动作块的执行和接手后的重新规划，和对齐读取一样，是"怎么在这个站点上正确地行动"的语义，也属于腰，不属于某座桥。

今天的方法仓库不必为了迁到新的读取接口而重写。腰上的读取接口做好之后，新方法直接用；老方法到下一次自己需要改时再迁。

### 8.4 约定：让数据能汇到一起

**【改】** 核心不定义动作空间和相机名，这是对的：换一台机器人核心不能改。但如果两台站点各自给流起名、各自选单位，它们的数据就不能放进同一个数据集，同一个 checkpoint 也不能换一台站点运行，积累就停在一台站点上。

所以加一种可选的、公开维护的**本体约定**（profile），例如 `yam-bimanual-3cam/1`：写明有哪些流、各叫什么、单位、动作的含义、相机的位置名。

- 站点清单声明自己遵守哪个约定。启动时按约定检查设备的描述，这是一项契约。
- 数据集记下成员遵守的约定；腰上的读取接口按约定映射，于是遵守同一约定的站点之间，数据和 checkpoint 可以通用。
- 约定由社区提出和维护，有版本，放在生态包里。核心只认识"声明了一个约定，并按它检查"，不认识任何具体约定。

**建造条件：** 第二台站点出现的时候，逐际就是这个时机。只有一台站点时，约定没有可比的对象，定下来也没人检验。

### 8.5 没有机器人也能参与

**【改】** 一个仿真设备：用设备描述里已经声明的 MuJoCo 模型，发布与真机相同名字、相同约定的流。它和真机走同一个站点、同一个协议。

它让没有硬件的人能开发方法和接入、能在 CI 里测试桥和客户端、能学习这套系统。它不用于验收：方法和功能的验收只认真机。

**建造条件：** 有一个具体的使用者。在那之前不建，因为一个仿真设备要跟着真机的流、约定和模型一起维护。

### 8.6 外来的数据

**【改】** 研究常常把自己的数据和别人的数据合在一起：公开的 LeRobot 数据集、其他实验室的录制、UMI、第一人称视频。今天 Episode 只能由站点产生。

改为：Episode 的头里，`station` 换成更一般的**产生者**；站点是一种产生者，导入是另一种。导入是一次运行：它读外部的数据（`https://`、`oss://` 等引用），写出 Episode，头里记下来源。这样外来的数据和自己的录制同样有血缘、同样能进数据集、同样能被判断。

它不必在冻结之前做：头里增加一个可选的 `producer`，`station` 照旧保留，按兼容规则这是追加。冻结时只要保证没有任何地方假定"每条 Episode 都来自站点"。

**建造条件：** 第一个真的要进数据集的外来数据集。UMI / Ego 的可行性说明可以先写。

### 8.7 复用而不重算

**【改】** 运行记录已经写明"读了什么、用了什么代码、写了什么"，这本身就是缓存的键。

- **导出和训练**：运行前先查有没有读了同一个数据集、同一个提交、同样参数的成功运行，有就直接用它的输出。`xpisode_format` 提供按 `read` 查运行的接口。今天四个方法各自把同一个数据集导出成 LeRobot 格式，以后只需要一次。
- **评测**：只在同一批内比较的规则不变。但真机时间最贵，每次都重跑旧模型做基线是浪费。计划可以放一个固定的**锚点**候选：每一批都带上它，外部的统计就能借它把不同批次连起来，也能发现站点本身是否在漂移。核心只提供"计划里标一个候选为锚点"，在那之前用自由键 `x_` 写就行，第二批评测时再看要不要标准化。
- **存储**：无损原始数据是一切派生的源头，但不是每一条都需要永远保留原样。转码是一次运行；原始文件在远端有校验副本、并且有了转码之后，可以按数据集的决定移出本机。**【你定】** 原始数据是否在远端也有保留期。

### 8.8 面向社区

不急，但今天的选择不能把门槛垫高。四条约束，现在就要守住：

1. **不要求 OSS，也不要求阿里云。** 只有一台机器、没有对象存储时，一切照样工作。`store/` 是普通的文件，相对路径就是对象的键，所以同步目标可以是任何"不覆盖已有文件"的复制方式：另一个目录、rsync、rclone、S3。格式才是接口，`scripts/oss.py` 只是其中一种实现。
2. **读数据不需要面板，也不需要站点。** 一个库加一个目录就够了。
3. **社区用户只需要认识四个名词：** Episode、数据集、判断、运行。其余的概念都藏在工具里。
4. **规则卡要有英文版。** 其余对外开放之前必须做的：
   - 规范和入门文档的英文版；
   - 清楚的许可证；
   - 发布的 wheel，不需要 Rust 工具链；
   - 一个不接硬件也能跑起来的演示站点（`examples/fake_station` 已经有了）；
   - 约定和桥的提出、评审、版本规则。

### 8.9 训练和推理一致：回放站点

训练时模型看到的输入，由导出器从录制里算出；推理时，由客户端从实时的流里算出。两条代码路径只要有一处不同（缩放、颜色通道、取哪一帧、动作块从哪一刻算起），模型在真机上就会出问题，而且很难查。

**做法：回放站点。** 起一个站点，名字和正式站点不同；它的设备都是回放设备（`xpisode_device.playback`）：读一条录好的 Episode，按原来的节奏重新发出各路流，收到的目标只记下、不执行。策略客户端原封不动地连上来，走的是和真机完全相同的路径。站点照常录下一条 Episode，里面有回放的观测，也有策略每一刻提议的动作。

- `scripts/replay_check.py` 一条命令完成：从 Episode 自带的站点配置生成回放站点、运行、录制，比较策略提议的动作和原录制里实际执行的动作（每个关节的误差、时间偏差），写出报告和可以直接打开的视图。这次检查本身是一次运行，记在读写图里。
- 查看器里，策略提议的动作画成半透明的"影子"机器人，和实际的机器人并排；用的是设备已经声明的机器人模型。
- 回放站点不占任何相机和 CAN 总线，数据写在本机 `local/replay/` 下，不同步。
- 它检查的是两条代码路径是否一致，不是验收；验收只认真机。

研究员的规则卡上只多一句：上真机之前，在一条训练用的录制上跑一次回放检查。

## 9. 核心和外部的界线

| 腰（核心） | 边（桥，我们维护，独立版本） | 外部 |
| --- | --- | --- |
| 三项标准和参考实现 | LeRobot 和 HDF5/zarr 导出器 | 设备适配器、策略、特殊的导出器 |
| 对齐样本的读取；动作块的执行和接手 | 推理服务和 ROS 2 的桥 | 提醒怎么发出 |
| 中心、站点进程、现场流程 | 本体约定 | 血缘对比、一致性报告、统计 |
| 七种记录、引用、血缘的遍历、按 `read` 查运行 | 仿真设备 | 数据质量的任何判断 |
| 契约的执行，包括约定的检查 | 看数据用的代理文件（第 7.5 节） | 同步、清理、skill |
| HTTP API 的 v1 | | 面板（它只是 API 的一个用户） |

判断一样东西该放在哪，问四句：

1. 换一台机器人它还成立吗？
2. 拿掉它，核心还完整吗？
3. 它是在执行声明，还是在评价内容？
4. 它写的是"发生了什么"，是别人的习惯，还是研究的选择？

前三句决定核心和外部。第四句决定腰、边和参数：写"发生了什么"的放腰上，写别人习惯的做成边，研究的选择做成参数。

agent 是有名字的使用者，和人走同一个 API，受同一套负责方和授权约束。

## 10. 冻结和变更

冻结的：Episode 格式、设备协议、环境协议、`store/` 的路径规则、七种记录的格式、引用前缀、"声明一个本体约定"的方式。具体的约定、桥、读取接口不在冻结之列，它们有自己的版本。它们只能追加：读取方忽略不认识的键和取值，不改已有字段的含义，每种记录带格式版本。

不冻结的：索引、缓存、面板、全部外部工具。

**【改】** 冻结发生在第 11 节的两道闸门都通过之后。在那之前格式可以改，数据不保证保留。冻结之前的录制只作测试，除非你逐批另定。

**【改】** 要改冻结的东西，先改这份文档。代码注释里对 ADR 编号的引用（64 处）改为指向规范的章节。

## 11. 验证

**每一条契约都有两处检验**：自动测试里用会出故障的假设备（停帧、时间倒退、进程消失、迟到），真机上按下表做一遍。前者防退化，后者才算验收。

**闸门一：真机故障注入。**

| 做什么 | 应该看到 |
| --- | --- |
| 录制中拔掉一台相机 | 1 秒内中止，原因写明是哪台；提醒持续；相机插回后自动恢复 |
| 相机不在时按录制键 | 不开始，记下拒绝和原因 |
| 运行中把系统时钟回拨 10 秒 | 什么都不发生 |
| 杀掉一个机械臂的设备进程 | 控制组收回，录制中止，站点不就绪；`recover` 后恢复，不重启站点 |
| 手臂静止时杀掉站点进程 | 设备因租约过期停稳；重启后未完成的录制恢复为 `interrupted` |
| 把数据盘写到下限以下 | 录制中止，新的录制被拒绝 |
| 关掉提醒程序；操作员离岗 | 站点不就绪，原因各自写明 |
| 评测中重启面板 | 评测继续，游标不变 |
| 非负责方经 API 开始录制 | 被拒绝；授权后可以 |
| 起第二个站点抢同一台相机 | 后启动的被拒绝，说明被谁占用 |
| 删掉 `local/` 重启面板 | 索引重建，结果一致 |

**闸门二：整条回路走一遍。** 按第 8.1 节的表，用两个方法（服务器上微调 pi0.5，本机训练 ACT），从定任务到出结果，再做一次血缘遍历，确认两个结果都能走回同一个数据集、同一个站点、同一个任务版本。走的过程中每一处卡住、需要人工对齐、或者让人怀疑的地方都记下来；属于核心的修完才冻结。

## 12. 路线

按风险排，不按功能排。每一段结束时系统都比开始时更可信。

| 段 | 做什么 | 结束的标志 |
| --- | --- | --- |
| 0 现在 | 停掉当前的正式采集，或明说这些录制只作压力测试、不进数据集 | 操作员知情 |
| 1 守约 | 契约与 `blocking`、就绪、开始前拒绝、中途中止；SDK 的时钟换算和倒退处理；相机适配器离开系统时钟；启动前检查 | 带故障的假设备的自动测试全过 |
| 2 事实 | 负责方、`via`；"下一条"带判断；计划的完成规则；提醒由站点启动 | 录下来的"谁"和"完成"都是对的 |
| 3 接口 | HTTP API 加 `/api/v1/`；自由键的 `x_` 命名空间；规范从代码生成；每个依赖方一条静态检查 | 改一处核心，检查能列出所有要跟改的仓库 |
| 4 出口 | 同步的 `pull`、`verify`；只写本地的规则；余量和清理；编码实测；血缘遍历、按 `read` 查运行；删导出器登记 | 一个数据集能在服务器上读到，一个 checkpoint 能回到站点机 |
| 5 闸门一 | 真机故障注入，约两小时，需要操作员在场 | 表里每一行都留了记录 |
| 6 闸门二 | 整条回路 | 复盘里的核心缺陷清零 |
| 7 冻结 | 规范逐篇审过、打版本号、发布 wheel、内部说明、清理旧文档和分支 | 第二台机器能照文档装起来 |
| 之后，按条件 | 第 8.3 节表里的桥、本体约定、仿真、导入、锚点，各自到了建造条件才做；现场流程搬进站点进程、传感器自动恢复、站点日志 | 每做一项，先写明它的主人和删除条件 |

第 1 段之前不该再有正式采集。第 2、3 段会改录下来的事实和对外的接口，所以必须在冻结之前。其余的都是追加：放在冻结之后不会让任何数据作废，也不会让任何依赖方跟改。

现场流程搬进站点进程（第 4 节）是一次大改。按 M7 它不急：只要 HTTP API 的 v1 不变，以后搬的时候外面感觉不到。

**【你定】**

1. 站点机的 RTC 设成了本地时区，每次开机时钟先偏 11 秒再被拨回。改成 UTC 能去掉这个偏差，但如果这台机器还装着 Windows，会影响那边。第 5.2 节落实后这不再造成故障，但仍建议改。
2. 站点开机自启的来源（第 5.5 节）。
3. 图像编码和红外的去留，在实测之后（第 7.4 节）。
4. 每天打算采集几小时。这决定第 7.4 节的缓冲和上传够不够，也决定编码这件事有多急。
5. 这台站点是否允许无人值守，允许哪些程序（第 6.1 节）。
6. 原始数据在远端是否有保留期（第 8.7 节）。
7. 第一个本体约定由谁来定、怎么命名（第 8.4 节）。约定一旦有人用，就和格式一样难改。
8. 上线的版本号；冻结之后谁可以改冻结的格式。
9. 旧 ADR（现在在 `docs/archive/adr/`）留作历史还是删除；0015–0020 的原文在这台机器上找不到，如果别处有，值得对一遍。（已定：三篇留作历史，各自顶上注明。）

## 13. 和今天的实现相比，改了什么

| 方面 | 今天 | 这份设计 |
| --- | --- | --- |
| 就绪 | 控制时钟启动过就一直为真 | 由当前的契约算出，带原因列表（已做） |
| 必需的流 | 封存时记一条问题 | 不在就不开始，断了就中止（已做） |
| 设备故障 | 终态，重启站点 | 传感器自动恢复；执行器由操作员 `recover` |
| 时间戳 | 适配器各自换算，相机经过系统时钟 | SDK 统一换算，不碰系统时钟；单次倒退不致命（已做） |
| 采集和评测的流程 | 在面板进程里 | 在站点进程里 |
| 操作者 | 浏览器里的自由文本；按计划时写成 `plan` | 负责方的名字；入口另记（已做） |
| 谁能操作 | 能连上 API 的任何人 | 负责方，和它授权的人 |
| 判断 | 录完去面板上填；不填等于要 | 并入"下一条"；不填是单独的状态，默认不选（已做） |
| 计划的行 | 没被判为不要就算完成 | 正常结束并且判为要才算完成（已做） |
| 录制之外的事 | 不留记录 | 站点日志 |
| 提醒 | 外部脚本，没开就没有 | 清单里的必需客户端（已做） |
| 服务器写数据 | 没有规定 | 只写本地，再同步（已做） |
| 容量 | 没有表示 | 状态里有余量，低于下限拦住（已做） |
| 记录的种类 | 声称没有分类 | 七种，写明 |
| 冻结 | 走通之前 | 两道闸门之后 |
| 清单的 `use` 写法 | 已决定，未实现 | 不做 |
| 导出器登记 | 已决定删除，未删 | 删 |
| 接一个方法 | 方法仓库里写 700–2900 行导出器和客户端 | 多数方法只写一份配置，走共享的桥 |
| 数据汇合 | 每台站点自己起名，数据不能合 | 可选的本体约定，声明了就检查 |
| 无人值守 | 没有规定 | 清单允许时，程序可以负责；计划可以指定程序判断 |
| 外来数据 | 不能进 store | 导入是一次运行，产出有血缘的 Episode |
| 没有机器人的人 | 不能参与 | 仿真设备，用于开发，不用于验收 |
| 重复的导出和基线 | 每个方法、每批评测各算一次 | 按 `read` 查到就复用；评测带锚点 |

## 14. 想过但不采用的

| 方案 | 为什么不 |
| --- | --- |
| 核心加规则检查，判断数据好坏 | 是评价内容；和执行契约不是一回事 |
| 站点一直录，事后再切 Episode | 每小时一百多 GB，做不到；站点日志拿到了它最有用的那部分 |
| 一条 Episode 按流拆成几个文件，红外单独存取 | 写入、恢复、校验都要变成多文件；先看编码实测，够用就不拆 |
| 面板加登录和令牌 | 能登录站点机的人本来就能做任何事；要防的是意外，负责方和授权就够 |
| 所有设备故障后都自动恢复 | 机械臂出问题后不该无人监督地重来 |
| 强制每条录制都判断才能继续 | 自由录制时是负担；按计划时"下一条"已经是判断 |
| 用中心数据库保存血缘或流程状态 | 成为单点；脱离面板就读不了；状态应当能从记录算出 |
| 运行记录带种类字段 | 随研究方式变化的东西不该进核心的词汇 |
| 策略、遥操作走不同的路 | 接管就成了两套机制之间的切换 |
| 结束录制时顺便给出成败 | 判断要能事后更正，也要记下是谁；它是另一条记录 |
| 面板运行导出器和外部程序 | 把它们绑在站点机上，服务器无法照做 |
| 在核心里做排名和提前停止 | 比较是否公平由实验设计决定，框架不知道 |
| 录制器独立进程 | 为跨进程补的机制比它解决的问题多 |
| 框架提供标定工具、约定末端位姿流 | 前者实测精度不够；后者是能算出来的重复数据 |
| 每个方法自己写导出器和客户端（今天的做法） | 1.4 万行重复的接口代码，格式一改全部跟着改，没法复用 |
| 核心定义统一的动作空间和相机名 | 换一台机器人核心就要改；改为可选的、社区维护的约定 |
| 桥放进核心 | 推理接口和数据格式会随生态变化，核心不该跟着变；桥是独立版本的边 |
| 对齐读取也做成一座桥 | 它写的是"发生了什么"的语义，放在边上就会被每座桥各写一遍 |
| 桥里替方法做研究选择（动作标签、过滤） | 选择会被所有方法悄悄继承；选择应当是记在运行里的参数 |
| 判断页继续用 Rerun 全量视图 | 判断只要扫一眼，全量视图要转 9 路视频；Rerun 留给细看 |
| 仿真用于验收 | 验收只认真机；仿真用来开发和测试接入 |
| 外来数据作为另一种记录，不是 Episode | 进不了数据集，也没有同样的读取接口；它和自己的录制应当一视同仁 |
